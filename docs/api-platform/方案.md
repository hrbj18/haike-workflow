# 海客统一 API 服务方案

日期：2026-10-12；代码基线和状态见 [README](README.md)。本文是可供实施的设计，不代表支付、供应商网关或账本已上线。

## 1. 推荐产品形态

新增「海客 API 账户中心」与「运营后台」，配套云端统一网关。本地工作台只需填写公司网关地址和一个客户 Key，即可调用已开通的配音、声音克隆、数字人、ASR、生图、生视频及可选文本模型。

“一个 API”定义为**统一地址、统一身份、统一钱包、统一账单**。配音、上传、克隆与视频异步任务协议不同，内部保留对应能力接口；不能只换一个 OpenAI Base URL 就覆盖全部能力。

客户项目、最终成片、平台 Cookie、本地渲染和发布继续留在客户电脑。第三方供应商凭据只在公司服务器。用户有自备供应商账号时，可保留「自有 API」高级模式；这类调用不经过平台钱包，也不计入平台销售收入，页面明确标识计费来源。平台模式不能失败后悄悄切换自有 Key 或其他付费模型。

## 2. 用户体验和页面

### 2.1 完整使用流程

1. 在云端账户中心注册、登录，进入余额页。
2. 选择充值金额，创建付款订单，扫码支付；服务端确认到账后可用余额增加。
3. 在「API Key」页输入名称、用途、每日预算和可选到期时间，创建自己的 Key；明文仅展示一次。
4. 本地「统一 API」设置中粘贴 Key。正式发行可预填公司地址，客户只填 Key；开发环境允许显式配置可信网关地址。
5. 保存后自动读取账户摘要、余额与可用模型，展示「已连接」；连通检查仅做免费读取，不生成付费试听。
6. 生成前展示模型、用途、预计费用与上限。手动任务确认一次；批量 Agent 任务可事先设置项目/日预算，在有效授权和预算内自动执行。
7. 云端预占额度、执行任务、结算；本地获得结果及账单编号。余额和账单摘要自动刷新。
8. 客户随时打开完整账户中心查看充值、调用、冻结、退额和余额变化。

### 2.2 客户页面

| 页面 | 内容与操作 |
|---|---|
| 余额与充值 | 可用余额、冻结额度、实付/赠送拆分、本月净消费；充值订单和钱包流水分表 |
| API Key | 创建、命名、掩码、用途、模型范围、日/月预算、有效期、最后调用、撤销；接入步骤 |
| 模型与价格 | 名称、供应商、能力、模型/档位、计量单位、客户单价、最低计费量、可用状态 |
| 调用账单 | 日期、项目、任务、Key 名称、模型、用量、单位、单价、价格版本、冻结/实扣/退额；筛选与 CSV 导出 |
| 调用详情 | 本地关联任务、云端任务、分段/角色子任务、交付状态、计量证据、结算时间、失败原因、可恢复操作 |
| 账户设置 | 登录与会话、通知、充值退款申请、发票资料（按业务实际开通） |

页面必须区分“费用很小”和“免费”：小于 0.01 元时摘要显示 `<¥0.01`，详情显示至少 6 位小数或准确累计值。单位需随模型改变，不能把所有 TTS 一律写成字符。

建议普通用户导航中不出现运营页面。原型用于一起审阅，正式产品管理后台使用独立入口和服务端管理员权限。

### 2.3 自动连接和网页登录

本地保存 Key 后，受限账户摘要接口即可显示账户名、余额和该 Key 关联的用量。此体验满足“无需每次登录工作台”。完整账单、充值和 Key 管理使用云端网页登录会话，首次登录后记住会话；不能凭模型 Key 自动获得修改密码、创建新 Key、现金退款或管理员权限。

云端网页使用安全会话 Cookie（HttpOnly、Secure），写操作校验 CSRF/Origin。需要正式跨端登录时，使用系统浏览器的授权码 + PKCE；CLI 输入受限场景可用 device code。PKCE 本身不是现有项目已经实现的功能，需账户服务支持。参见 [RFC8252](https://datatracker.ietf.org/doc/html/rfc8252)、[RFC8628](https://datatracker.ietf.org/doc/html/rfc8628)。

Key 由本地后端保存并代理调用，浏览器不读取已保存的明文；优先系统钥匙串，兼容模式写入项目已有忽略的私有配置文件并限制权限。不得写 URL、浏览器 localStorage、任务清单、公开配置、截图或日志。公钥匙串接口选择留到实现时验证 Windows/Mac 支持。

## 3. 后台的业务结构

```text
客户工作台 / Agent ──一个客户 Key──→ 统一 API 网关
                                     │
              ┌──────────────────────┼──────────────────────┐
              │                      │                      │
          身份和权限           模型目录 / 报价          钱包 / 账本
                                     │                      │
                           持久化任务 / 提交记录 ← 原子冻结额度
                                     │
                           分能力队列与供应商适配器
                                     │
                  百炼 / 腾讯 / 豆包 / RunningHub / 其他
                                     │
                            私有产物与用量证据
                                     │
                           交付验证 → 结算 → 客户账单

账户中心 ──网页登录会话──→ 充值 / Key管理 / 完整账单
运营后台 ──管理员会话──→ 供应商配置 / 价格发布 / 成本核对 / 调账
支付渠道 ──验签回调──→ 付款事件 → 充值入账（幂等）
```

首版建议独立的 `api-platform/` 服务，用 FastAPI 延续现有 Python 技术栈；PostgreSQL 管理交易、账本及租户数据，Redis 仅用于缓存/限流/队列辅助，私有对象存储保存临时输入和交付产物。初期采用模块化单服务及独立 worker，避免立即拆成大量微服务。

现有 `backlot/server.py` 能读写本地项目并执行制作流程，不能直接作为公网多租户充值服务器部署。统一服务只接收明确的媒体输入、参数和客户身份，不允许远程指定本地文件路径、执行任意脚本或读取客户 Cookie。

## 4. 价格与差价

### 4.1 管理员如何设定比例

支持三种明确区分的定价方式：

- **成本基准 × 加价系数 + 服务费**：适合可可靠计量的字符、Token、图片等；成本基准是发布时锁定的目录价/合同价，不是每次实时变化的供应商余额。
- **按目标毛利率定价**：基础售价 = 定价成本基准 ÷ (1 − 目标毛利率)；支付、流量等费用需要纳入基准或另行核算。
- **固定客户售价**：按任务、音频秒数或固定档位收费，平台承担实际上游成本差异；适合 RunningHub 的产品档位。

例：成本基准 1 元、系数 1.3 → 售价 1.30、价差 0.30、基础毛利率约 23.08%。目标毛利率 30% → 基础售价约 1.428571 元。不要把“加价 30%”标成“毛利率 30%”。这些是假设数字。

一条价格版本保存：能力、provider/model/profile、地域、币种、计量分项、每份包含单位数量、成本依据及核对时间、加价系数、固定服务费、舍入规则、客户层级、生效时间、发布人。客户只看客户价；后台才看成本和毛利。

管理员先编辑草稿，预览不同用量的售价，确认后发布新版本。已有报价在有效期内沿用旧版本；已接受任务一直按冻结版本结算。价格发布和修改供应商凭据分别授权、留审计。

### 4.2 按项目实际模型计量

| 能力/模型 | 客户计量 | 报价与结算要求 |
|---|---|---|
| `cosyvoice-v3.5-flash` 配音 | 供应商有效字符 `usage.characters` | 分段总用量，不能用文本长度代替最终回执；定义预占上限 |
| `qwen-audio-3.1-tts-flash` 配音 | 输入、输出 Token 分项 | 没有可靠输出上限时首版暂不开放变量后付费；可选固定产品价并由平台承担成本偏差 |
| 文本/视觉云模型 | 输入/输出/缓存 Token 等 | 非重叠的计量分项，指定输出 Token 上限，流式中断仍获取最终可核实用量 |
| ASR | 指定模型返回的 Token 或计费时长 | 当前百炼适配器按 Token 估算；腾讯等按各自规则，不能统一假定“每分钟” |
| 声音克隆 | 次数或明确服务包 | 按模型实际规则；创建、审核及附带试听是否额外收费均写入报价 |
| RunningHub 数字人 | 固定 profile 的每角色/每秒/每任务产品价 | 上游实际按资源/执行费核对；音频时长不能冒充上游计算耗时 |
| 生图、生视频、音乐 | 张/秒/任务及规格 | 分辨率、张数、时长、模型和质量冻结，逐供应商验收 |

当前源码中的 `lib/bailian_speech.py::tts_cost()` 返回的是 **float 目录价估算**，并非客户账单或供应商实付。保留作本地参考，正式交易全部改由云端固定精度计量；不能读 `estimated_cost_cny` 后直接给客户扣款。官方 CosyVoice HTTP 返回有效字符用量和请求 ID，产物 URL 有有效期，因此服务端须及时转存并保存证据。[官方 API](https://help.aliyun.com/zh/model-studio/cosyvoice-tts-http-api)

所有供应商成本标记 `estimated / accrued / confirmed / unknown`，不知成本时显示待核对，不能算成 0。供应商优惠、免费额度、包月额度、汇率与合同价会影响实际成本；用平台制定的公开售价收费，并在后台核算实际采购成本。

### 4.3 金额精度与上限

内部统一 CNY 整数微元：`1元 = 1,000,000 micros`、`1分 = 10,000 micros`；数据库 BIGINT，JSON 金额使用十进制字符串，避免 JavaScript 大整数丢精度。单价计算用 Decimal/有理数，最终一次任务合计再按约定舍入到微元，不能每个字符/分段先向上进位到分。

微信付款仍为整数分 `amount_fen`。旧离线包协议 `_minor` 定义是分，绝不能改变含义；新平台采用 `/v2` 与 `haike-api-v2-draft`，新字段用 `_micros`。旧 mock 若保留，则保持 `/v1` 与原行为。

动态费用任务必须提供 `max_charge_micros`，服务器预占足以覆盖约定用量上限的金额。供应商不能可靠限制上游开销时，客户扣费仍不得超过确认上限，平台承担超额成本；不可后台默默补扣。项目/日/Key 预算也是服务端原子校验；并发预占计入预算，避免几十个请求同时绕过限制。

时间在服务端保存为UTC，用户按账户时区查看，首期默认Asia/Shanghai。日预算按任务接受时所属预算周期冻结，结算/释放回写同一周期，不因跨午夜或客户端改时钟绕过限制；同时保留账户资金与并发总约束。

## 5. 钱包、支付与账本

### 5.1 钱包展示

总未消费额度 = 可用 + 冻结；实付和赠送分别保存。首版可只上线实付余额，数据库预留赠送类型；首版不做转账、提现、用户间余额交易。

余额 100 元，任务预占 10 → 可用 90、冻结 10，总额仍 100。
实际结算 8 → 可用 92、冻结 0，总额 92、本次实际消费 8。
任务确定失败且未扣款 → 释放冻结 10；称“已释放”，不是现金退款。
已经扣款后经核实需返还 → 一次任务退额，账单保留原结算与调整，净消费 0。

### 5.2 充值闭环

首期建议微信 Native；支付宝作为同接口支付适配器后续增加。此为设计默认，正式开通取决于实际商户主体、签约和通知域名。

1. 服务端创建充值订单并确定金额、币种、客户和商户订单号；前端显示付款二维码。
2. 微信通知按原始请求体验签、选正确公钥/平台证书，解密 resource；验签不通过不入账。
3. 验签后先可靠持久化事件，再快速应答；数据库或事件存储失败不能回应已接收成功。
4. 持久化事件处理器检查商户、应用、平台订单、支付交易号、CNY 金额及 SUCCESS 状态；同一事务更新订单、创建账本凭证、增加余额。
5. 对 `payment_provider + provider_transaction_id`、商户订单以及充值入账业务事件建立唯一约束，重复通知只返回原结果。
6. 前端轮询订单状态，不按“扫码完成”或浏览器跳转入账。回调遗漏时主动查询；每日核对渠道付款/退款与账本。

微信要求及时验签应答、支持重复通知并结合查询补偿，以上可靠事件与入账事务是本方案的实现建议。[微信官方支付回调](https://pay.weixin.qq.com/doc/v3/merchant/4012791882)

现金退款先核对未消费、未冻结且未被其他退款占用的实付余额，冻结退款金额后发原路退款。支付退款未知时不再次申请新退款，按原退款号查询；成功后最终记账，确定失败再释放。不能退款期间继续消费同一笔余额。赠送额度不作为现金退款基数。

### 5.3 账本约束

采用不可变复式流水，余额为事务内维护的投影，能从流水复算。每个凭证同币种借贷平衡；管理员不能直接修改钱包数值。更正使用有理由、关联原凭证及操作者的补偿凭证。

示例业务凭证（不是完整企业财务报表）：

| 事件 | 借方 | 贷方 |
|---|---|---|
| 充值 100 | 支付清算 100 | 客户可用余额负债 100 |
| 冻结 10 | 客户可用余额负债 10 | 客户冻结余额负债 10 |
| 结算 8、释放 2 | 客户冻结余额负债 10 | 服务收入 8、客户可用余额负债 2 |
| 未扣款失败释放 10 | 客户冻结余额负债 10 | 客户可用余额负债 10 |

同一事务：锁定客户钱包与预算行 → 检查额度 → 写幂等记录/任务/报价接受状态 → 写冻结凭证 → 写 outbox。worker 从 outbox 取得可执行任务。仅靠 Redis 锁不能保证账本一致；并发锁顺序固定，数据库唯一约束负责资金事件去重。

平台利润按已交付收入与真实采购成本计算；充值形成服务余额，不直接当利润。支付手续费、存储流量、失败后平台承担的供应商费用单列。成本待核对的部分不能显示为已确认利润。

## 6. 调用、恢复与交付

### 6.1 一个计费任务的状态

```text
上传/参数校验 → 报价 → 确认 → 原子冻结 + 创建任务
→ queued → submitting → running → delivering → succeeded
                  ↘ submission_unknown → reconciliation_pending
                                   ↘ 核对后回到执行或确定失败
running → cancel_pending → cancelled / running / succeeded
确定失败 → failed；释放未扣额度，已扣错误以调整凭证返还
```

任务状态与资金状态独立：`reserved / settled / released / refunded / reconciliation_pending`。资金待核对不能伪装已经退款。失败前可知调用未提交则安全释放；提交结果未知不按本地超时自动释放。

### 6.2 幂等与断点恢复

- 本地在提交前持久化随机 `call_intent_id`、冻结输入哈希、报价、上限。恢复沿用原 ID；禁止用当前时间、重启次数或新 Key ID 重新生成。
- 服务端幂等范围是客户账户 + 操作 + 幂等键；同键同内容返回原任务，内容不同 409。同一个 quote 只能接受一次，换幂等键也不能二次扣款。
- 服务端创建提交记录后才向供应商发起调用；获取供应商 ID 后及时保存。没有供应商幂等支持时，进程在受理后保存前崩溃仍可能未知，必须核对，不能承诺分布式绝对只执行一次。
- 本地提交响应丢失：按原幂等键查询公司网关；服务端向供应商提交未知：按已记录线索、供应商回执与管理核对处理，禁止盲目重提。
- 分段 TTS 的每个供应商调用、用量和已完成音频分别保存；只恢复查询/下载/拼接。新内容或用户明确重生成才新建收费任务。
- Key 撤销禁止新任务；已接受任务仍按原约定完成并计费。客户使用同账户新 Key 或网页会话找回旧任务，不能因撤销 Key 丢失账单。
- 已完成云产物在公布的保留期内可重新下载，不新建模型调用。过期只剩本地产物则使用本地文件；需要重新生成时给新报价。建议首版云产物保留 7 天，可配置，页面显示实际到期时间。

### 6.3 本项目的交付边界

本地父视频任务包含配音、数字人、合成等多个阶段。**每个云能力独立计费**，不会把整片失败自动解释成所有已成功云服务退款。

例如配音已完整交付并结算 0.20 元，双主持数字人角色 B 失败：数字人计费任务按“两个角色完整交付”规则净收费 0，平台承担该任务上游损失；之前已交付的配音账单仍为 0.20 元，客户可恢复利用音频。

RunningHub 固定 profile 继续冻结工作流 `2094449979141218305`、`infinitetalk_448x560_exact_clock_v2`、Plus、448×560、25 FPS、角色数和准确帧数；两个角色分别记录上游 ID，可并发执行，完整交付后结算。云端验证文件可解码、规格/时钟/角色匹配与 hash；本地另做下载与导入校验。不要仅凭 HTTP 200 或存在一个 URL 认定完成。

取消请求不是取消成功；供应商已执行而不能取消时，按原先约定和交付结果结算。用户客户端不能自报失败直接触发退额，服务端必须持有终态证据；争议走独立核对记录。

文本流式等已分次交付能力单独明确收费规则，不能套用数字人完整产物退款规则。首版可先关闭云端文本流式，在钱包与媒体闭环稳定后再开放。

## 7. 数据模型与权限

| 表/实体 | 关键内容与约束 |
|---|---|
| users、accounts、account_members | 登录身份、客户账户、归属；首版个人一账户，预留团队 |
| sessions、api_keys | 网页会话与模型 Key 分离；Key前缀+高熵随机秘密的不可逆校验值、scope、预算、过期/撤销 |
| wallets、wallet_balances | account/currency/资金类型；available、reserved 非负及 version；能从账本重建 |
| ledger_transactions、ledger_entries | 不可变业务凭证和借贷分录；business_event 唯一、同币种平衡；调整引用原凭证 |
| recharge_orders、payment_events、cash_refunds | 付款/退款号、金额、状态、验签后的事件、渠道原路退款恢复 |
| providers、provider_credentials | 地域/业务空间/账户池、加密凭据与版本；仅后台有权管理 |
| models、service_profiles、price_versions | 能力可用状态、约束、公开售价、内部成本基准与冻结版本 |
| quotes、jobs、job_children | account、输入哈希、单次报价接受、上限、交付状态、客户费用与本地关联 |
| usage_items、supplier_operations、cost_receipts | 非重复用量分项、上游提交/ID、证据、成本待核对/确认 |
| files、artifacts、voices | 客户归属、用途、大小、hash、生命周期；音色绑定模型和创建时上游账户/空间 |
| idempotency_records、outbox_events | 客户+操作+键唯一；接受任务与可靠调度同事务 |
| audit_events、billing_disputes | 调价、Key、调账、退款、人工核对记录与处理人 |

所有受保护记录都从认证身份确定 account_id，不能接受用户请求体随意指定账户。音色、文件、任务、退款和账单逐对象鉴权；跨账户 ID 拒绝。不同租户相同文件 hash 不能暴露彼此文件是否存在；缓存和复用按租户隔离。

上传实施大小/媒体类型限制、真实解析、用途校验和生命周期。网关下载外部产物只走供应商允许域名并防止访问内网；客户不可传任意下载 URL 让服务器取内部资源。原始文字、声音、图片留存按明确保留期和客户授权；运营成本日志默认不保留完整正文/密钥/带签名 URL。

## 8. 运营后台

1. 供应商渠道：配置 Key、地域、工作空间和模型权限；读取连通检查免费。真实生成测试另走有报价的测试任务，不藏在“测试连接”按钮里。
2. 模型上架：供应商、模型、单位、输入限制、profile、验收证据；`planned/testing/available/disabled` 四态，只展示真实可卖能力。
3. 定价：成本来源核对 → 草稿/比例预览 → 发布版本 → 查看已确认收入、已确认/待核对成本及基础毛利。
4. 资金：充值到账、冻结异常、支付对账、充值退款、任务退额；调账和现金退款要求更高权限，建议复核。
5. 任务：按客户/能力查询，处理提交未知与取消待核对，不能通过“重试”按钮生成第二次上游任务。
6. 审计与告警：供应商余额低、失败率、资金挂账、账本不平、异常用量；不能只看充值金额当盈利。

## 9. 分阶段实施与验收

| 阶段 | 实施内容 | 出口 |
|---|---|---|
| M1 账户与资金底座 | 登录、Key、模型目录、微元账本、报价、任务与故障模拟、用户中心 | 并发不透支、幂等不重扣、跨租户拒绝、状态可恢复 |
| M2 支付和首个模型 | 单支付渠道签约/联调；先 CosyVoice 字符配音，再声音克隆 | 真实小额充值和生成→账单→退额闭环，回调/账本对账 |
| M3 数字人 | 固定 RunningHub profile、双角色、准确时钟、未知提交/取消核对 | 正常交付与部分失败均正确结算，旧任务恢复不新付费 |
| M4 扩展供应商 | Token TTS、ASR、生图/视频/音乐、可选云文本/视觉 | 每个模型分别验收；一个Key覆盖已上架项，禁止空壳上架 |

真实联调需要实际公司域名/服务器、支付商户资料和供应商凭据；当前设计没有使用或申请这些秘密，也没有触发真实费用。上游业务服务条款和素材/声音使用授权按实际服务确认，不将“已有适配器”当成已经允许商业转售。

验收必须包含：重复/乱序支付通知、错误金额/商户/币种、通知遗漏查询补偿；100个并发预占不透支；同 quote 换键不能重复接受；账户相同幂等键隔离；调价不改旧单；Key 撤销/轮换恢复；分段 TTS 与双主持部分失败；未知受理不盲目重提；重启恢复；下载重试不收费；退款申请与消费竞争；微额与借贷平衡；成本未知不计为零；本地处理不产生模型消费。

建议先跑通“充值 → Key → CosyVoice 配音 → 费用明细”，再扩展更多模型。这条链路可检验整个商业系统，避免供应商数量很多但余额与结算仍不可靠。
