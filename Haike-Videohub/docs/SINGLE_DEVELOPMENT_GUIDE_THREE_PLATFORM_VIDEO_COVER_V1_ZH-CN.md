# 单次开发指导文档：三平台视频与专属封面可靠发布

状态：开发前方案，尚未实施与验收  
编写日期：2026-09-24  
适用仓库：Haike_video、creatorhub、Haike-Videohub  
本轮样例：阿里真武 V900 的 9 秒成片和新生成的 3:4 AI 封面；样例只用于准备和最终受控验收，不作为自动实发测试。

## 1. 本次要解决的问题

目标是让一条经审核的视频与其**指定的专属封面**作为同一个发布包，可靠地发布到抖音、快手、视频号；提交前能阻止不完整的任务，提交后能区分“平台收到了视频”“封面设置成功”“作品列表上的实际封面已核验”。网络中断或平台结果不明时，系统能恢复同一任务，不能靠重建任务碰运气。

本次开发完成后，用户应能看见每个平台的最终标题、描述、视频和封面、发布时间与位置设置、任务编号、封面核验状态以及下一步处理办法。要求 AI 专属封面时，原视频帧不能被静默当作替代品。

## 2. 开发目标与边界

| 编号 | 目标 | 完成时的可观察结果 |
|---|---|---|
| G1 | 发布包固定视频、专属封面、来源和三平台文案 | 每个平台任务可追溯到同一发布包及文件 SHA-256 |
| G2 | 指定封面任务在提交前严格校验 | 缺图、损坏、比例错误、路径不可读、文件变更或封面设置失败，都不会点击平台发表 |
| G3 | 平台写入和验收状态清楚分开 | 界面与 API 分别展示平台提交结果、封面结果和作品列表核验结果 |
| G4 | 重试不会产生第二条作品 | 同一提交编号返回同一任务；提交结果不明时先核对原任务和作品 |
| G5 | 平台差异在发布前可见 | 视频号 16 字标题与空位置处理、抖音/快手实际文案均有预检读回 |
| G6 | 旧任务可安全读取，新任务走新契约 | 历史任务保留原语义并标记“封面未核验”，不在迁移时自动重发 |

本轮实现范围是同机部署的 Haike → CreatorHub → 三个平台发布链。AI 生图继续使用当前已经配置的生图入口；本轮只规定生图结果如何进入发布包和如何核验，不重做图像生成服务。平台审核结果依赖创作者后台，代码不能把平台“上传成功”冒充为“审核通过”。视频号、抖音和快手都不做无条件自动后补或自动重发。

## 3. 关键产品判断

### 3.1 封面策略

新发布包提供 cover_policy，取值 required 或 optional。Haike 发起且用户指定封面、特别是要求 AI 封面时，固定为 required；只有用户明确接受平台自动选帧时才为 optional。旧客户端不传该字段时保留兼容路径，但界面不得将其展示为“封面已验证”。服务端应提供版本/能力查询，Haike 在提交新契约之前检查支持情况，避免旧服务忽略新字段却直接发布。

图片来源记录为 generated_ai、provided_image 或 approved_video_frame。generated_ai 需要保留生成服务与模型标识、生成时间、原始文件和最终 3:4 文件的哈希；**该标识是来源证据，不是封面质量证明**。最终图片以实际像素、字形、裁切及平台预览判断。默认不自动换用历史封面或视频首帧。

### 3.2 发布包及文件固定

在 Haike 侧建立一个版本化发布包，含 package_id、视频路径与 SHA-256、封面路径与 SHA-256、来源类别、三平台账号/标题/描述/话题、公开范围、位置意图、审核与素材授权记录、创建时间。凭据、Cookie 和媒体二进制不写入共享仓库。发布包与回执放在项目的忽略目录；字段契约写在正式源码和跨仓契约中。

准备完成后生成不可变的本地媒体快照或同等的内容寻址文件。CreatorHub 接单和真正上传前都核对哈希；若文件被替换，任务在触发平台写入前失败。视频与封面必须为同一 package_id 的固定版本，修图则产生新版本，不能悄悄改已有任务的文件。

拟定的新请求字段为 contract_version=2、package_id、package_revision、expected_platform、video_sha256、cover_sha256、cover_origin、cover_policy、location_mode（clear/set/keep）和原有的媒体路径、文案、账号。客户端还要在 HTTP 头携带稳定的 Idempotency-Key。服务端首先比对 expected_platform 与账号实际平台，再校验媒体哈希。能力查询至少返回 contract_version、三个平台的 required 封面支持情况及验收字段版本。正式实现前先确定字段名和历史客户端的默认值，在两仓写同一份契约测试。

### 3.3 提交边界和结果状态

沿用现有发布任务 ID 和服务端 Idempotency-Key。Haike 在发 HTTP 请求前持久化 package_id、平台、账号、payload 摘要和提交编号。超时后先凭提交编号重放或查询原回执，不能换号再发；相同提交编号但内容不同返回冲突。一个平台只对应一个正在处理的发布任务。

仅靠提交编号还不足以防误发：客户端可能丢失原编号。服务端再以 package_id、package_revision、平台、账号建立唯一任务约束。相同发布包即使用了新编号，也返回原任务或明确冲突；真正要重新发布须增加发布包版本，并在创作者后台确认旧作品的状态。

三个发布器在点击“发表”之前，应调用已有持久写入标记或等价机制。标记失败不点击；标记成功而点击结果不明，任务进入 uncertain，人工检查原作品后再处理。提交前的封面失败是可安全修复的准备失败；提交后的封面或作品核验失败是待核查状态，不能自动重传视频。

建议独立保存 cover_status（未要求、待设置、预览已确认、失败、未知）和 acceptance_status（待核查、已核验、需人工处理）。沿用原 publish status 表示任务执行，不用单个 done 代表“视频和封面都正确”。历史任务迁移后的验收状态为“未核验”。目标封面的验收要比对目标文件或其可识别视觉指纹，不能只看预览“发生变化”。

### 3.4 平台页面读回

设置封面后，优先比较页面预览与目标图的可判定特征；无法稳定判定时，不替 required 任务作成功结论。发布后再用创作者后台的**唯一目标作品**核对标题、视频身份和实际缩略图，并记录核验时间和证据位置。平台卡片一时不出现时保持待核查；若平台审核中，单列审核状态。允许有证据的人工核验，但要记录核验人、时间和对应作品 ID。

视频号位置字段要表达“清除位置”“设置指定位置”两种意图。未指定位置时，发布器仍需读当前页面并清除默认 POI，再读回确认；否则拦截 required 发布包。视频号短标题按 16 字及页面字符校验展示最终值，不把服务端 20 字上限当作平台最终标题。

## 5. 任务拆分与顺序

| 任务 | 内容与主要落点 | 交付物 / 退出条件 |
|---|---|---|
| T0 基线 | 核对运行配置、相关 dirty diff、现有任务及封面测试 | 确认不会覆盖他人改动，列出当前旧预期 |
| T1 发布包 | Haike 新建发布包模型和准备入口，保存来源、哈希、三平台元数据、授权记录 | 离线生成包；修改文件能检出版本变化 |
| T2 预检 | Haike 适配器校验媒体与封面、平台最终标题、位置意图、账号平台、服务端能力 | dry-run 展示真正会提交的值；required 不合格时阻断 |

## 6. 具体开发流程

1. 写出发布包和 CreatorHub 请求/响应的版本化字段表，明确 required 与旧任务的兼容规则。先约定错误码：封面缺失、封面无效、哈希变化、预览未知、账号平台不符、提交结果不明。
2. 实现 Haike 离线准备和 dry-run。展示每个平台最终标题、描述、位置意图、封面来源、文件哈希、将调用的服务端能力。此阶段不能有 POST /api/publish。
3. 接入持久提交编号和服务端能力协商。服务端不支持严格契约时，提交直接报错；不能退化为旧式 best-effort 路径。保留原回执，超时后复用同一编号。
4. 增加服务端字段与 SQLite 向前兼容迁移，覆盖历史 pending/done 任务的读写。旧任务不做批量再执行，也不伪造核验通过。
5. 将三个发布器的封面结果改为结构化结果，在点击发表前判定。为每个平台接上持久写入标记；点击后的异常一律进入待核查流程。消除“未知等于成功”的分支。
6. 修正视频号位置和标题读回。页面变化时返回可理解的错误、截图及安全恢复点，不靠固定睡眠推定成功。
7. 实现作品列表唯一定位和目标封面核验；无法唯一定位、页面未同步或正在审核时保留待核查状态。任何后补操作必须确认是同一作品，不自动创建新视频。
8. 更新 UI/CLI 用语及旧测试；再更新相关契约。现行知识库手册由获委托的维护者根据实测证据修改，本开发先提出需要替换的条目与证据。
9. 按下节从纯离线到受控真号逐层验收，保存每个平台任务 ID、实际作品 ID、标题、视频和封面证据。验收失败只修当前失败平台与任务。

## 7. 测试方法和验收标准

### 7.1 离线与集成测试

在 creatorhub 仓库使用临时配置和假浏览器运行针对性测试。现有测试入口为 tests/test_channels_cover.py、tests/test_douyin_cover_live.py、tests/test_kuaishou_cover.py、tests/test_access_and_submissions.py、tests/test_write_gates.py、tests/test_test_isolation.py。增加的新测试须断言“最终发表按钮点击次数”和“持久任务数”，不能只检查日志或函数返回串。

在 Haike_video 仓库给发布包、适配器和提交回执增加独立测试，使用临时目录和假 HTTP 服务。测试不连接 127.0.0.1:8000 的运行实例。先运行相关测试，再运行受到修改影响的既有测试；需要验证跨仓接口时使用独立临时 CreatorHub 服务。真实账号、真实 Profile、真实媒体和真实 POST /api/publish 不进入自动测试。

建议执行命令（开发后按实际新增的测试文件调整）：

    cd creatorhub
    .venv/Scripts/python.exe -X utf8 -m pytest -q tests/test_channels_cover.py tests/test_douyin_cover_live.py tests/test_kuaishou_cover.py tests/test_access_and_submissions.py tests/test_write_gates.py tests/test_test_isolation.py
    cd ../Haike_video

针对性测试通过后，再运行两个仓库各自完整测试套件和适用的文档/上下文检查。若环境缺少依赖，记录具体缺项及未执行范围；不能把“未运行”写成“通过”。

### 7.2 故障注入矩阵

| 输入或故障 | 必须观察到的结果 |
|---|---|
| 缺失、坏图、非 3:4、来源不符、文件哈希变化 | required 预检失败；没有创建平台任务或没有发表点击 |
| 预览未变化、预览探针未知、浏览器弹层遮挡、上传超时 | 发表点击数为 0；保留任务和可用诊断信息 |
| 写入标记持久化失败 | 发表点击数为 0 |
| 已标记写入、点击超时或进程中断 | 同一任务进入 uncertain/需核查；自动重试次数为 0 |
| 创建请求超时后客户端重发相同编号 | 服务端只存在 1 条任务，返回原任务 ID |
| 相同编号换用另一封面或视频 | 返回冲突，不修改原任务 |
| 两条作品标题相同、列表暂未同步、缩略图仍为视频帧 | 不判定封面验收成功；不重发视频 |
| 视频号页面已有默认 POI，意图为清除 | 发表前确认页面 POI 为空；否则阻断 |
| 旧库升级、历史任务读取 | 任务及媒体路径保留，封面状态为未核验；无自动发表 |

### 7.3 具体验收标准

| 编号 | 达成标准 | 验收证据 |
|---|---|---|
| AC-01 | 新发布包保存视频/封面两个 SHA-256、封面来源、三平台最终文案与账号；版本变化可追踪 | 包结构与读回断言 |
| AC-02 | 要求 AI 封面时，缺图或用视频帧顶替均阻断；有效 3:4 新图才通过 | 正反例夹具和 dry-run |
| AC-03 | 发布前缺图、坏图、哈希变化及三平台封面预览失败时，无平台发表点击 | 三个平台各自的假浏览器计数 |
| AC-04 | 三个平台的预检值与实际填写值一致；视频号标题 ≤16 字且空位置被清除 | 页面桩读回；真号截图复核 |
| AC-05 | 同一提交编号在超时、重启、并发和重放时仅有一个任务 ID；同一发布包换编号仍不能创建第二单；不同内容冲突 | 临时 SQLite 并发与 API 测试 |
| AC-06 | 写入标记在发表前持久化；标记后未知结果不自动重试 | 故障注入与重启恢复测试 |
| AC-07 | 任务 done 不自动等于封面通过；API/界面能显示提交、封面、作品核验各自状态 | 响应字段、列表页面与测试截图 |
| AC-08 | 作品列表定位不唯一或缩略图不匹配时，状态为需核查，且无第二次发表 | 两条同名作品和错图夹具 |
| AC-09 | 旧数据库和旧任务升级后可读取，原任务不重发，未核验状态清楚 | 旧库副本迁移测试 |
| AC-10 | 三平台受控实发各只有一条目标作品；逐一核对实际视频、最终标题、目标封面及位置 | 每平台任务 ID、作品 ID、后台截图与人工核验记录 |
| AC-11 | 当前源码、契约、UI 文案不再把 POST /api/publish 称为“只创建草稿” | 文案核查与相关测试 |
| AC-12 | 上述针对性测试和受影响的回归测试通过，失败项有复现和修复证据 | 测试报告及变更清单 |

AC-01 至 AC-09、AC-11、AC-12 属于代码交付门；AC-10 是上线/真实平台行为验收门。代码门通过但 AC-10 未做时，只能称为“实现并通过离线验收”，不能称为“三平台可靠发布已实测”。AC-02、AC-03、AC-05、AC-06 任一失败则本次开发不合格。

## 8. 受控验收与恢复

真实发布验收仅在本次公开发布授权、样例素材使用范围、三个账号状态和最终发布包均已核对后执行。先查三平台是否已有同一作品，再逐个平台使用同一发布包提交一次；保存任务 ID 并等待原任务结果。平台页面需要扫码或人工处理时记录现场并停在同一任务。视频号先确认封面与位置，再点击发表。若作品进入审核中，记录为待核查，不能立即判为 AC-10 通过。

回滚边界以“是否已经触发平台发表”划分：发表前可修复同一任务并重新预检；发表后只核对/修复该作品，无法确认时保留 uncertain，不删除回执、不换编号重发。若平台确实发布了错误封面，先定位唯一作品，再使用平台支持且经核实的封面编辑入口；无法安全修改时报告真实状态与处理选择。
