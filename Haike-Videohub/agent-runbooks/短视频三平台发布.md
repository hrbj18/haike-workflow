# 短视频三平台发布操作手册

状态：已实测（2026-09-24 用同一 v2 发布包完成抖音、快手、视频号各一条视频，三平台作品列表的指定 AI 封面均已核验；2026-09-29 同链路按小时排期发布 21 条 v1 任务，抖音／快手／视频号的平台侧二次核对均命中）。
最近核验：2026-09-29。
适用范围：用户明确要求把指定成片发布到抖音、快手和／或视频号。Haike 自动制片只产出待审视频；公开发布是独立的、由用户发起的任务。
核验条件：2026-09-24 的本地 Haike／CreatorHub 代码、三个已登录账号与平台页面；2026-09-29 复用同一 CreatorHub 副本与同三账号发布 21 条（含已修脚本 `_sched0929.py` 合并写、持久盯梢 `_watch929_all.py`）。精确 Git 提交号未记录，其他代码版本、账号或页面状态必须重新核对。
完成证据：发布任务 `done`，并在对应平台作品列表找到目标作品，逐项核对标题、视频和实际缩略图是否与目标封面一致；v1 任务（无必需封面）至少要有发布器落下的**平台侧二次核对**证据（见 §3）。仅有 `done`、发布成功提示或管理页 URL 都不足以证明发布成功。此状态不保证以后平台行为不变。

权威入口：Haike_video 的 `../Haike_video/AGENT_GUIDE.md` 与 `../Haike_video/backlot/publish_adapter.py`、[指定封面发布契约](../contracts/publish-v2.md)、[历史契约](../contracts/publish-v1.md)、[CreatorHub 启动步骤](../steps/05-creatorhub.md)。冲突时核对正在运行的服务版本与用户本次授权。

## 1. 确认目标与去重

1. 固定本次的项目 ID、**确切 MP4 版本**、目标平台、账号、标题、详情、话题和封面。检查文件存在且非空，用 `ffprobe` 看时长、尺寸、视频和音频流；为视频及封面记下 SHA-256。发布过程中不要悄悄换文件。

   **★ 任务持有的是「路径」不是「快照」**（2026-09-29 实证）：任务把媒体绝对路径存进 `media_json`，发布时**直接读盘**、不复制副本。因此——
   - `contract_version=1` **不锁定成片 SHA-256**：成片被同名覆盖（返工重出）后，**旧任务发出去的就是新片，无需重建**。
   - `contract_version=2`（必需封面包）在**提交时和发布前各校验一次** `file_sha256(video) == video_sha256`：成片一旦变化，旧任务会在发布前直接判 `failed`（「成片已与发布包记录不一致」），**必须重建任务**。
   - 返工替换成片后，先查当前任务的 `contract_version`／`cover_policy`／`video_sha256` 再决定是否重建；v1 无需重建，盲目重建反而可能撞上发布包唯一约束。
2. `GET http://127.0.0.1:8000/api/accounts` 读取实时账号状态；账号 ID 从结果取得，不复用旧任务里记下的数字。`invalid` 或登录态失效时先恢复登录，再重新检查。
3. `GET http://127.0.0.1:8000/api/publish` 查同一项目／视频的既有任务。`done` 平台不重发；`publishing` 和 `uncertain` 等待核对，不能重新创建。一个平台失败不影响已成功的平台。
4. 对来源片段逐一记录使用范围。`unknown` 时可准备封面、发布包和 dry-run，不能创建公开发布任务；确认后修订发布包版本并记录依据。本轮 V900 测试已由用户确认素材可用于发布，实际提交包的来源状态为 `confirmed`。

## 2. 准备封面和文案

- 每个平台分别写 `title`、`desc`、`topics`。标题可能被 CreatorHub 或平台截断，dry-run 后还要核对当前发布器代码与最终提交值。详情开头放主题关键词，因为部分管理页卡片主要展示详情。涉及价格与性能时写明比较基准，核对厂商原始公告。话题通过 CreatorHub 的 `topics` 字段提交，不把一长串话题塞进标题。
- 准备 **3:4 竖封面**，检查实际图片、字形和裁切。封面路径必须是 CreatorHub 进程可读的本地绝对路径。视频号作品的封面／描述修改机会有限，发布前就把最终版本确定好；严禁用不确定的列表定位去改旧作品。
- v2 发布包要求 `cover_policy=required` 时，抖音、快手、视频号在最终发表前遇到封面上传失败、预览未变化或无法确认均停止。旧 `contract_version=1` 任务仍按历史可选封面流程处理。`done` 和 `cover_status=applied` 均不是最终作品封面验收结果。
- 视频号未指定位置时，新发布包使用 `location_mode=clear`；发布器必须在**发布表单**的“位置”字段读回“不显示位置”，无法确认时停止。2026-09-24 实测页面曾预填城市；视频预览也显示同名城市，不能用全页第一个城市文字或宽泛类名定位表单。旧任务仍可能继承页面默认 POI。
- 视频号短标题预检会规范化常见标点并截到 16 字；严格发布器填写后读回。页面字符规则以真实页面校验为准。
- 需要 AI 封面且使用本机中转站时，按当前生图技能查询可用模型与成本，再生成和核对最终图片；不复用历史任务的模型 ID。
- 原片画面也可在用户接受时用作封面素材。无论来源如何，都在发布前打开最终 3:4 文件核对，不依赖上传成功提示推断封面正确。

## 3. 提交与观察

提交前对竖屏视频做平台 UI 叠加检查，至少包含顶部搜索/导航、右侧操作栏、底部作者与描述；按实际视频视口核对缩放/裁切。人物、核心产品信息、标题和逐句字幕须避开遮挡。数字人版式按[数字人口播视频](数字人口播视频.md)，不要用本地播放器无按钮的预览替代此项。模拟 UI 通过与实际手机播放通过分别记录。

1. 如 `127.0.0.1:8000` 不可达，按 `steps/05-creatorhub.md` 启动已配置的 CreatorHub，再查账号和任务。
2. 在 `Haike_video` 仓库根目录，用 `python backlot/publish_adapter.py --video <绝对路径> --platform <平台> --account-id <实时账号ID> --title <最终标题> --desc <最终详情> --topics <话题> --cover <3:4绝对路径> --cover-origin generated_ai --cover-proof <生成证据JSON绝对路径> --source-rights-status unknown --dry-run` 分平台核对最终 payload、哈希、位置意图和告警。若封面不是 AI 生成，按实情选择 `provided_image` 或 `approved_video_frame`。三平台共用同一个发布包 ID 与媒体哈希。
3. 素材使用范围确认后，修订发布包，再按实情使用 `--source-rights-status confirmed` 或 `owned`。提交前查 `GET /api/publish/capabilities`；旧服务不能执行 v2。用户已授权本次公开发布且 payload 正确时，用同一参数加 `--commit --i-know-this-creates-a-real-task` 提交。CLI 在交互终端再次要求输入 `yes`。保存任务 ID 与 `.backlot/publish-receipts/` 回执；超时重跑须复用同一回执与编号，先查原任务，不换编号另建任务。`POST /api/publish` 可能立即发表。
4. 按任务 ID 读取 `GET /api/publish`：`pending` 时先观察调度；`publishing` 时等待，不重复提交或重复触发；`uncertain` 时停止自动重试并人工核对；`failed` 时根据具体错误修复后先确认平台上没有同一作品；`done` 再到对应创作者作品列表核对标题和封面。v2 任务不能删除或修改媒体与封面，以保留去重回执。`result_url` 可能只是管理页，不一定是作品直链。
5. 抖音、快手、视频号的作品列表核验走各自创作者后台。只在唯一定位目标作品后核对实际视频、标题、缩略图和位置；作品 ID 从后台列表响应或作品详情只读提取，不能用任务 ID 代替。CreatorHub `PUT /api/publish/{tid}/acceptance` 记录作品 ID、本机证据路径及四项核验结果；`verified` 只能用于四项均通过。每个平台记录任务 ID、作品 ID、状态和封面证据。2026-09-24 的人工/只读探针作品核验已实测；跨平台自动作品定位与图片比对仍需独立验证。
6. 当前 CreatorHub 发布器用全局 `Semaphore(1)` 串行运行发布流程，三平台任务不会并行；视频号发布器的上传就绪检查上限为 900 秒（15 分钟）。这是等待上限，不是正常时长承诺。长时间 `publishing` 时先查同一任务与发布日志，确认停在上传、封面、提交还是作品列表核验阶段；不要并发再发或新建重试任务。每次执行前复核当前服务源码，上限和并发策略可能变化。
7. **平台侧二次核对证据按平台分流在两份日志里**（2026-09-29 踩过，导致误判「视频号没有证据」）：抖音／快手发布器用 `print`，写在 `data/logs/codex-publish-stdout.log`；**视频号发布器用 logging，写在 `codex-publish-stderr.log`**。只 `grep` stdout 会得出错误结论。证据形态：
   - 抖音：跳作品管理页 → 搜索框命中标题；
   - 快手：发布接口回包 `result=1` ＋ 作品列表接口命中标题；
   - 视频号：`[ch-publish] 平台核对: found=True 作品列表接口命中标题「…」(N 个响应)`；失败时才落 `data/debug/ch_publish_<tag>_<ts>.png`，**当日无此类文件可反证未走失败分支**。
   - 发布器在**发布前**还会先查重（`发布前查重: found=False` = 列表无同标题，可安全发）。
   - 任务的 `acceptance_*` 字段可能整列为空／`not_checked`，**不能靠它**判定，只能看上述日志与平台后台。

## 4. 完成证据

每个目标平台的任务为 `done`，且对应创作者后台能找到目标作品；核对实际标题、视频和封面。`pending`、上传进度完成、接口返回成功或仅有管理页 URL，都不足以单独证明发布完成。未能核对的平台单独报告为待核验，不重发已成功的平台。

v2 作品核验时，对**唯一目标作品**保存实际后台截图，再向 `PUT /api/publish/{tid}/acceptance` 提交 `work_id`、`evidence_path`（本机可解码截图绝对路径）、`unique_work`、`video_matches`、`title_matches`、`cover_matches` 和可选 `note`。只有任务 `done` 且四项检查全为 `true` 才记为 `verified`；重复标题、缩略图不同或截图缺失时填真实结果并保留 `needs_review`。不能拿预览页封面代替作品列表的实际缩略图。

## 5. 已遇到的故障

已授权发布完成后，可在唯一定位的作品播放页补充实际遮挡证据，记录设备/视口和当前 UI。此项是画面呈现核验，独立于现有 v2 的四项作品验收字段；不得伪造接口字段或用它替代封面验收。用户手动发布时，可使用其提供的播放截图。不能为了验证布局额外上传、重发或删除作品。2026-09-28 真实抖音截图发现旧圆框被搜索栏遮挡；新三秒模板通过不代表新全片已通过平台验收，快手/视频号同类遮挡尚未验证。

| 现象 | 处理 |
|---|---|
| CreatorHub 端口拒绝连接 | 核对服务进程，按安装启动文档启动，重新探活；创建请求失败时先查任务列表再决定是否重试。 |
| 视频号账号 `invalid`、鉴权返回 `300334` | 在 CreatorHub 恢复该账号登录，实时检查 `active` 与登录态；不为另外两个已成功的平台重发。 |
| 图像中转站报 `model_not_found` | 查询 `/v1/models` 的 ID，分别确认文字驱动模型和图像模型；不盲猜别名。 |
| 创建任务后返回 `pending`，很快变成 `publishing` | CreatorHub 可能自动调度。只观察同一任务 ID；不要因一次接口响应而再次创建。 |
| `publishing` 长时间没有新日志或结果 | 同时查 `/api/publish` 和 `/api/task-queue`，检查发布器最后一条日志与作品管理页。当前代码全局串行发布；视频号上传就绪检查最多等待 900 秒。任务仍运行时不要提交第二单；平台结果未明确时记为待核验，保留原任务 ID。超出当前源码中的等待上限仍无结论时，先检查现场截图和同一作品列表，不得只因超时就重试。 |
| 任务 `done`，但目标作品缩略图仍是原视频画面 | 保留原任务和回执，标记作品核验为需处理。抖音可先用 CreatorHub 仓库的 `python -m scripts.backfill_cover probe --account <账号ID> --platform douyin --search <唯一标题片段>` 只读定位；确认唯一作品后才考虑后补封面。后补可能触发重新审核；定位不唯一或预览未变化时停止。旧任务的 best-effort 封面尤其需要此核查。 |
| 视频号短标题出现红色特殊字符提示、发表按钮不可用 | 按发布页提示替换不支持的符号（本次把中文逗号改为空格），确认标题不超过当前 16 字限制后再处理。任务 `failed` 时，先到作品列表确认作品不存在；仅在用户已授权发布、且确认无作品后修正原失败任务并观察原任务，不要再创建第二条。其他符号的限制待平台页面复核。 |
| 视频号封面编辑器“确认”被加载遮罩挡住 | 不凭点击超时判失败。先读回发布页封面预览；保存诊断截图。先核对任务与平台作品，再决定是否恢复同一任务，不能直接新建第二单。 |
| 发布页出现视频处理／上传等待 | 等待平台处理并观察同一任务；完成判据是任务 `done` 加作品列表核对，不能只看上传进度。 |
| 快手封面上传前的缩略图截图卡在字体加载 | required 封面任务会在发表前失败。先查后台没有同一作品及任务未触发发表；当前发布器可通过缩略图 URL 解码像素取得基线，截图为回退。修复后仅恢复原失败任务，核对最终作品列表封面。2026-09-24 同一任务恢复实测成功。 |
| 抖音「没能打开竖封面封面编辑器」连续失败（2026-09-26） | 编辑页灰度 new-layout 布局后：① 封面区被挪到右栏、与「发文助手」浮卡重叠，Playwright 命中测试被拦 → 已加 JS 原生 `el.click()` 兜底；② 「选择封面」打开的是嵌在预览框里的封面选择器，老弹层遗留 input 喂了不生效（像素指纹三轮不变=假成功）→ 已改为真鼠标点击上传入口 + `expect_file_chooser` 投喂；③ 页面文本含零宽字符（U+200B），精确文案匹配必须先剥离。失败现场看 `creatorhub/data/debug/dy_cover_*.png/txt` 与服务日志 `[dy-cover]`（启动服务时 stdout 已落 `_server_*.log`）。修复后仅恢复原失败任务，发表前拦截的任务平台侧不会有作品。 |
| 视频号位置字段预填城市，但清除流程找不到“不显示位置” | 保留原失败任务，不直接发表。先检查发布页截图：左侧视频预览和右侧发布表单可能同时出现同名城市；仅操作表单的位置控件，选“不显示位置”并读回。发表前失败且后台无同一作品时，修复代码后恢复原任务。2026-09-24 实测通过。 |
| 快手作品管理页 `?status=2`（已发布）筛选显示「共0个作品」，作品实际已发布（2026-09-26） | 平台筛选参数与列表状态展示不一致。改开「全部作品」页签（`/article/manage/video` 不带 status 参数）核对：新作品状态列为「已发布」。作品 ID 从列表接口 `rest/cp/works/v2/video/pc/photo/list` 响应的 `workId` 字段提取（注意该接口字段是 `workId`，不是发布回包的 `photoId`，两套字段名并存）。 |
| `grep` 发布 stdout 日志找不到视频号核对证据（2026-09-29） | 视频号发布器走 logging，输出在 **stderr** | 改查 `data/logs/codex-publish-stderr.log`；不要据此判定「视频号未发布」。见 §3 第 7 条。 |
| 作品同步接口（`/api/accounts/{id}/works/sync`）返回「未抓到作品／未拦截到作品数据」 | 该平台 sync 实现限制，**与登录态无关**（同日同一账号的发布链路刚用作品列表核对成功过） | **不要用 sync 失败反推登录态失效**；改用该平台发布器的作品列表核对，或账号页实测。 |
| 盯梢脚本日志文件长时间不增长 | 脚本可能只在状态跃迁时打印，静默期不写日志 | 先确认脚本有无心跳行；**不要仅凭日志 mtime 判定进程已死**，改用进程存活 ＋ 心跳行判断。 |

## 6. 维护边界

本手册保存当前流程，不保存账号密钥、Cookie、固定浏览器选择器或某一条作品的完整日志。v1 的批量排期（同轮多平台错开写入间隔、任务 `scheduled_at` 存 **UTC**）与 v2 的必需封面、视频号位置清除均已实测；跨平台自动作品定位和自动图片比对尚未实测。批量排期依赖当前 CreatorHub 的风控间隔配置与调度器行为，配置或服务版本变化须重新核对。平台页面或服务版本变化时，先依据当前代码与页面复核。重复发布由发布包唯一约束和持久回执拦截，但操作前仍须查已有作品与任务。
